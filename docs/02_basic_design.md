## 1. 概要

### 1.1 目的

Suno で生成した楽曲（シングル／アルバム）を対象に、**生成由来のアーティファクト（シャリシャリ音、ヒス、こもり等）を除去したうえで、配信に最適な音圧・音質に仕上げる**マスタリングツールを提供する。

### 1.2 対象ユーザー

| ペルソナ | 特徴 | 求めるもの |
|---|---|---|
| P1：Suno クリエイター（非エンジニア） | マスタリングの知識は少ない。配信したい | ワンクリックで「ちゃんとした音」にしたい。何が良くなったか見てわかりたい |
| P2：DTM 経験者 | Logic 等を使える。耳が肥えている | 自動の結果を細かく調整したい。メーター・差分で検証したい |
| P3：アルバム制作者 | 複数曲をまとめてリリースする | 曲間の音量・音色を揃えたい。曲順・曲間も決めたい |

### 1.3 スコープ

**対象**
- 入力：Suno の WAV（48kHz/16bit 等）、MP3（非推奨。警告を出す）、ステム（Suno Studio の書き出し）。ブラウザへのドラッグ＆ドロップ、またはファイル選択で取り込む
- 処理：解析、Suno クリーンアップ、マスタリング、アルバムの自動バランス
- 確認：プレビュー再生、A/B 比較、波形（前・後・差分）、メーター
- 出力：WAV / FLAC / MP3 / AAC、アルバムの連続ファイル、CUE、レポート

**対象外**
- AI 生成の痕跡を検出させないための処理（配信事業者の検出回避、ウォーターマーク除去）※倫理・規約上の理由
- 作曲・アレンジの変更、ボーカルの差し替え
- 配信サービスへの直接アップロード
- DDP の書き出し（後のフェーズで検討）

### 2.2 非機能要件

| ID | 区分 | 要件 |
|---|---|---|
| NFR-01 | 性能 | 4分の曲を標準モードで処理する時間：**M1 の Chrome で 30 秒以内、Safari で 45 秒以内**（目標） |
| NFR-02 | 性能 | パラメーターを変えてから、表示中の範囲（ループ範囲）が聴けるようになるまで：**1 秒以内**（目標） |
| NFR-03 | 性能 | A/B 切り替えは**途切れず、再生位置を保ったまま**行う（再生中に即座に切り替わる） |
| NFR-04 | 性能 | 波形の描画は 60fps でズーム・スクロールできる |
| NFR-05 | 品質 | 出力は指定した True Peak の上限を**必ず**守る（4倍以上のオーバーサンプリングで検証） |
| NFR-06 | 品質 | 内部処理は 32bit float 以上。ビット深度を落とすときはディザを入れる |
| NFR-07 | 品質 | 処理は再現できる：同じ入力・同じ設定なら同じ出力になる |
| NFR-08 | 安全性 | 元のファイルは変更しない（非破壊） |
| NFR-09 | プライバシー | 処理はすべてブラウザ内で行う。音源・解析結果・プロジェクトをサーバーへ送信しない（アクセス解析も入れない） |
| NFR-10 | 信頼性 | タブを閉じたりブラウザが落ちたりしても、プロジェクトの状態を復旧できる（ブラウザ内ストレージへの自動保存） |
| NFR-11 | 使いやすさ | 初めての人でも「取り込み → 書き出し」を **3クリック以内**でできる（Auto Master の経路） |
| NFR-12 | アクセシビリティ | 色だけに頼らない表示（形・パターン・ラベルを併用）。キーボードだけで主要な操作ができる |
| NFR-13 | 保守性 | DSP モジュールはプラグイン的な構造にし、追加・差し替えができる |
| NFR-14 | 互換性 | D9 のブラウザで同じ機能が使える。ブラウザの差は「保存方法」など最小限にとどめ、非対応の機能は代替手段を用意する |
| NFR-15 | 記憶容量 | ブラウザのメモリ使用量：1曲の編集中 1.5GB 以下。ブラウザ内ストレージの使用量を表示し、不要なキャッシュを削除できる |
| NFR-16 | 可用性 | インターネットに接続していなくても使える（ローカル実行のため。外部のサーバーや CDN に依存しない） |

## 3. システム構成

### 3.1 全体アーキテクチャ（D1・D3・D8）

```
 ┌─────────── ローカルサーバー（自分の Mac 上。http://localhost:5173）──────────────┐
 │  HTML / JS / WASM / プリセット JSON を配るだけ。音源は一切受け取らない              │
 │  COOP/COEP ヘッダーを付与（SharedArrayBuffer を使うため）                         │
 │  インターネットには公開しない                                                    │
 └───────────────────────────────┬──────────────────────────────────────────────┘
                                 │ 同じ Mac のブラウザから開く
┌────────────────────────────── ブラウザ（1タブ）────────────────────────────────────┐
│                                                                                │
│  ┌──────────── メインスレッド（React + TypeScript）────────────┐                  │
│  │ 画面 / 状態管理 / 波形描画（Canvas2D・WebGL2）/ メーター描画    │                  │
│  │ Orchestrator：ジョブ管理、プロジェクト保存、再生の制御          │                  │
│  └──────┬──────────────────────────────┬───────────────────────┘                  │
│         │ postMessage（転送可能なバッファ） │ SharedArrayBuffer（音声・制御）           │
│  ┌──────▼──────── DSP Worker × N ──────┐ ┌▼───────── AudioWorklet（再生）──────┐    │
│  │ Rust→WASM の処理エンジン            │ │ Before / After / Delta / Ref の     │    │
│  │ 解析 / Suno クリーンアップ /         │ │ 同期再生、A/B 切り替え、ループ、      │    │
│  │ マスタリング / アルバム / 表示用データ │ │ ゲイン合わせ、メーター計算            │    │
│  └──────┬─────────────────────────────┘ └────────────────────────────────────┘    │
│         │                                                                        │
│  ┌──────▼───────── ブラウザ内ストレージ ─────────────────────────────────┐          │
│  │ OPFS：取り込んだ音源のコピー、レンダリング結果のキャッシュ、表示用データ    │          │
│  │ IndexedDB：プロジェクト（設定、曲リスト、スナップショット、解析結果）        │          │
│  └──────────────────────────────────────────────────────────────────────┘          │
└────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 構成要素ごとの責務

| 構成要素 | 責務 | 主な技術 |
|---|---|---|
| UI（メインスレッド） | 画面表示、操作、波形・メーターの描画 | React, TypeScript, Zustand, Canvas2D/WebGL2 |
| Orchestrator（メインスレッド） | ジョブ管理（優先度・キャンセル）、プロジェクトの保存、Worker と AudioWorklet の制御 | TypeScript |
| DSP Worker | 解析と DSP によるレンダリング（非リアルタイム）、ファイルのデコード・エンコード | Rust → WebAssembly（SIMD）、Web Worker |
| AudioWorklet | 再生（同期・切り替え・ループ・ゲイン）、リアルタイムメーター | Web Audio API, SharedArrayBuffer |
| ストレージ | 音源・キャッシュ・プロジェクトの保存 | OPFS（Origin Private File System）, IndexedDB |
| ローカルサーバー | アプリのファイルを localhost で配る（COOP/COEP ヘッダー付き） | Vite（開発用サーバー／ビルド結果のプレビュー） |
| ML（P4、任意） | ステム分離、帯域拡張 | ONNX Runtime Web ＋ WebGPU（第一候補） |

### 3.3 技術選定の理由

- **ブラウザ内処理（D1）**：音源（1曲 50〜100MB）をアップロードしなくてよいので、すぐに処理を始められ、プライバシーも守れる。サーバー費用もほぼかからない。プレビューのたびにサーバーと往復しないので、操作への反応が速い。
- **Rust → WebAssembly**：ネイティブに近い速度（SIMD を利用）で DSP を動かせる。**同じコードをネイティブでもビルドできる**ので、DSP のテストやゴールデンテストは Mac 上で高速に実行できる。
- **Web Worker で処理し、AudioWorklet で再生**：重い処理が画面の操作や再生を止めないようにする。再生用の音声は SharedArrayBuffer で共有し、コピーせずに A/B を同期して切り替える。
- **OPFS**：大きな音声ファイルを高速に読み書きできるブラウザ内のファイルシステム。Chrome / Edge / Safari のすべてで使える。
- **ローカル実行（D8）**：サーバーの用意やアクセス制限が不要で、すぐに始められる。`localhost` はブラウザから安全な環境（secure context）として扱われるので、SharedArrayBuffer・OPFS・AudioWorklet などの機能は公開サイトと同じように使える。COOP/COEP ヘッダーはローカルサーバー（Vite）の設定で付ける。
- **ブラウザ内のデータは「URL のオリジン」ごとに分かれる**ため、起動する URL を `http://localhost:5173` に固定する（ポート番号を変えたり `127.0.0.1` で開いたりすると、別のアプリとして扱われ、保存したプロジェクトが見えなくなる）。
- **将来公開する場合**：Cloudflare（Workers の静的アセット配信 ＋ Access によるメンバー限定）を第一候補とする。アプリはブラウザ内で完結しているので、配置先を変えるだけで公開でき、設計の変更はほぼ不要。
- **Python について**：製品には含めない。ただし P0 のアルゴリズム試作と較正（試聴しながらの値の調整）には、使い慣れた numpy/scipy を使ってよい。

### 3.4 ブラウザごとの差（D9）

| 機能 | Chrome / Edge | Safari | 対応方針 |
|---|---|---|---|
| 書き出し先の選択（File System Access API） | 使える | 使えない | Safari は通常のダウンロードで保存する。アルバムは ZIP にまとめる |
| OPFS | 使える | 使える（書き込みは Worker から） | 書き込みはすべて Worker で行う |
| SharedArrayBuffer | COOP/COEP で使える | COOP/COEP で使える | 必須とする。使えない環境ではエラー画面を出す |
| WebAssembly SIMD | 使える | 使える | 必須とする |
| 出力デバイスの選択（setSinkId） | 使える | 使えない | 使えるブラウザでだけ設定項目を表示する |
| AAC エンコード（WebCodecs） | 使える | P0 で確認 | 使えない場合は AAC を選択肢から外す |
| WebGPU（P4 の ML） | 使える | 使える | P4 で検証 |

## 4. 処理パイプライン

### 4.1 全体の流れ

```
[取り込み] → [解析] → [自動設定] → [Suno クリーンアップ] → [マスタリング] → [アルバム調整] → [レンダリング] → [書き出し]
                ▲                        └────── ユーザー調整（マクロ/詳細） ──────┘            │
                └────────────────────────── 再解析（処理後） ◀────────────────────────────────┘
```

### 4.2 信号チェーン（1曲あたり）

| 段 | モジュール | 内容 | 既定 |
|---|---|---|---|
| 0 | Input Conditioning | デコード、内部 float 化、DC 除去、内部サンプルレート（48kHz）への統一 | ON |
| 1 | **Suno Cleanup** | 5章を参照（De-click → De-hiss → Shimmer Reduction → De-ess/Resonance → Mud Control） | ON（強さは自動） |
| 2 | Corrective / Tonal EQ | 目標トーンカーブ（ジャンル別、またはリファレンス曲）に向けたリニアフェーズ EQ ＋ 手動バンド | ON |
| 3 | Dynamics | マルチバンドコンプ（3〜4バンド、穏やか）、任意でトランジェント復元（潰れたアタックの補正） | ON |
| 4 | Saturation | 倍音付加（キャラクター：Clean / Warm / Tape） | OFF |
| 5 | Stereo | M/S バランス、低域モノラル化（既定 120Hz 以下）、幅の調整、相関の監視 | ON |
| 6 | Limiter | True Peak リミッター（オーバーサンプリング、ルックアヘッド）、目標 LUFS への自動ゲイン | ON |
| 7 | Output | SRC（44.1kHz 等）、ディザ（TPDF、任意でノイズシェーピング）、形式変換 | 書き出し時 |

- 各段は「バイパス」「ソロ（その段の効果だけを試聴）」ができる。
- 処理順は固定（MVP）。並べ替えは将来の検討事項とする。

### 4.3 自動設定（Auto Master）のロジック概要

1. 解析結果（6.1）から、問題の指標（シマースコア、ヒスレベル、こもり指数、PLR、相関など）を算出する
2. 指標を、閾値表または回帰モデルで各モジュールのパラメーターに変換する
3. 目標ラウドネスとシマーの強さから、クリーンアップの強さを補正する（音圧を上げるほど強めにかける）
4. 一度レンダリングして処理後を再解析し、目標との差（LUFS、TP、トーン）を確認。差が大きければ最大2回まで補正する
5. 結果を「提案」として表示する（ユーザーはそのまま採用することも、調整することもできる）

## 5. Suno クリーンアップ設計

### 5.1 モジュール構成

| サブモジュール | 対象（リサーチ資料 3.1） | 方式の概要 | 主なパラメーター |
|---|---|---|---|
| De-click | A4 クラックル | 突発的なノイズを検出し、補間で置き換える | 感度 |
| De-hiss | A3 高域ヒス | 静かな区間からノイズの特性を推定し、高域だけにスペクトルゲーティング | 量、下限周波数（既定 8kHz） |
| **Shimmer Reduction** | A1 シマー、A10 | 高域（既定 6〜16kHz）の STFT 振幅について、**時間方向の揺らぎ（フレーム間の変動）を検出してスムージング**。トランジェントは検出して保護する | 量、帯域、トランジェント保護 |
| De-ess / Resonance | A2 フィズ、A5 歯擦音 | ダイナミックなレゾナンス抑制（soothe 型）＋ ディエッサー（5〜10kHz） | 量、帯域、鋭さ |
| Mud Control | A6 こもり | ダイナミック EQ（200〜500Hz）。こもりの指数が高いときだけ効かせる | 量、中心周波数 |
| [任意] Stem-aware | A1/A5/A10 をパート単位で | ステム（入力または分離したもの）ごとに上記を適用し、再合成する。ボーカル・シンバルを重点的に処理 | パートごとの量 |
| [将来] Bandwidth Restore | A9 帯域の欠け | ML（Apollo/AudioSR）による高域の再構築。実験的機能 | ON/OFF、量 |

### 5.2 マクロ「Cleanup」

- 0〜100% の1本のノブで、上記サブモジュールの量を連動させる（自動設定で求めた配分比を保つ）。
- 既定値は解析結果から自動で決める（目安 50〜70%）。
- **かけすぎの警告**：処理後の高域エネルギーが元より大きく減った場合や、トランジェントが減った場合に「こもっている可能性があります」と表示する。

### 5.3 アーティファクトの検出指標（解析でも使用）

| 指標 | 意味 | 算出方法（概要。詳細設計で確定する） |
|---|---|---|
| Shimmer Score | シマーの強さ | 6〜16kHz のスペクトルについて、フレーム間の変動の大きさと、トーン性の低さ（スペクトル平坦度）を組み合わせる |
| Hiss Level | 高域ノイズフロア | 静かな区間の 10kHz 以上のレベル |
| Fizz Index | 5〜8kHz の耳障りさ | 帯域エネルギーの、目標カーブからの超過量とピークの鋭さ |
| Mud Index | こもり | 200〜500Hz の、目標カーブからの超過量 |
| Bandwidth Cutoff | 帯域の上限 | スペクトルが急に落ちる周波数の検出 |
| Crest / PLR | 潰れ具合 | ピークとラウドネスの差 |
| Mono Compatibility | 疑似ステレオ | 相関係数、モノラルにしたときのラウドネス低下量 |

## 6. マスタリング設計

### 6.1 解析（Analyzer）の出力

- ラウドネス：Integrated / Short-term の時系列 / Momentary の時系列 / LRA / True Peak / PLR
- スペクトル：平均スペクトル（1/6 オクターブ）、時間 × 周波数のスペクトログラム（表示用に縮小したもの）
- ステレオ：相関係数の時系列、帯域ごとの幅
- セクション：エネルギー変化による区間の推定（イントロ / サビ等の大まかな区切り。ループ範囲の候補に使う）
- アーティファクト指標：5.3 のとおり
- 波形ピーク：複数解像度の min/max/RMS（8章で使用）

### 6.2 ラウドネス目標プリセット（D6）

| プリセット | Integrated | True Peak 上限 | 用途 |
|---|---|---|---|
| **Streaming（既定）** | -14 LUFS | -1.0 dBTP | Spotify / YouTube / Amazon / Tidal |
| Apple | -16 LUFS | -1.0 dBTP | Apple Music 中心 |
| Loud | -10 LUFS | -1.0 dBTP | EDM / ヒップホップ / ロックなど音圧重視 |
| Dynamic | -16〜-18 LUFS | -1.0 dBTP | アコースティック / バラード / ジャズ |
| Custom | 任意 | 任意 | |

### 6.3 キャラクタープリセット

| 名前 | 方向性 |
|---|---|
| Clean | 透明。最小限の補正 |
| Warm | 低中域を厚めに、高域は穏やか。軽いサチュレーション |
| Bright | 高域の抜け（クリーンアップの後にダイナミック EQ で） |
| Punch | トランジェントの復元、中低域の密度 |
| Wide | ステレオ感を強める（モノラル互換性の監視つき） |

ジャンルプリセット（Pop / Rock / EDM / Hip-Hop / Ballad / Acoustic / Anime・J-Pop など）は「目標トーンカーブ＋キャラクター＋ラウドネス」の組み合わせとして定義する。

### 6.4 マクロコントロール

| マクロ | 操作範囲 | 連動する主なパラメーター |
|---|---|---|
| Cleanup | 0〜100% | 5.2 のとおり |
| Tone（Warm ⇔ Bright） | -100〜+100 | チルト EQ、高域シェルフ（クリーンアップ後）、低中域 |
| Punch | 0〜100% | マルチバンドコンプのアタック/比率、トランジェント復元 |
| Width | 0〜150% | Side ゲイン、低域モノラル化の周波数 |
| Loudness | 目標 LUFS | リミッターの入力ゲイン（TP 上限は固定） |

## 7. アルバム自動バランス設計

### 7.1 考え方

- 目的は「すべての曲を同じ LUFS にする」ことではなく、**アルバムとして自然に聞こえる相対バランス**を作ること。
- Spotify はアルバム再生時にアルバム単位で正規化するので、**曲間の相対差がそのままリスナーに届く**。

### 7.2 処理ステップ

1. **全曲を解析**（6.1）
2. **アンカー曲を決める**：既定は最も音圧感の高い曲（ユーザーが変更可能）。アンカー曲をアルバムの目標ラウドネスに合わせる
3. **ラウドネスの相対設計**
   - 各曲の「意図した音量差」を推定する（例：曲全体の平均ではなく**最も大きい区間の Short-term LUFS**を揃える。こうするとバラードは自然に小さくなる）
   - 曲ごとに相対オフセットを手動で補正できる（±dB スライダー）
4. **トーンの揃え**
   - 各曲の平均スペクトルから、アルバム平均のトーンカーブを算出する
   - 各曲をアルバム平均へ **部分的に**近づける（既定の強さ 50%。0〜100% で調整可能）。曲の個性を残すため、緩やかな広帯域の補正だけを行う
5. **共通のチェーン ＋ 曲ごとの差分**
   - アルバム共通の設定（キャラクター、リミッターの性格、TP 上限）と、曲ごとの差分（クリーンアップの量、EQ の差分、ゲインのオフセット）の2層で持つ
6. **曲順・曲間・フェード**
   - 曲間の既定は 2 秒。曲ごとに 0〜10 秒で設定可能、クロスフェードも可能
   - フェードイン/アウトのカーブを選べる
7. **検証**：全曲を再解析し、外れている曲（LUFS・トーンの偏差が閾値を超えた曲）を一覧で警告する

### 7.3 アルバムの出力

- 曲ごとのファイル（ファイル名に曲番号を含める）
- 連続した1ファイル ＋ CUE シート（任意）
- アルバムレポート（全曲の LUFS / TP / LRA / トーンの偏差）

## 8. プレビュー・比較設計

### 8.1 プレビュー方式（D5：差分レンダリング方式）

```
パラメーター変更 ─(デバウンス 150ms)→ エンジンに優先レンダリングを依頼
   ① 現在のループ範囲（または再生位置の前後 ±15 秒）を最優先で処理
   ② 残りの部分をバックグラウンドで処理
   → 処理済みの部分から順に、再生エンジンのバッファを差し替える（途切れないようにクロスフェード）
```

- 各モジュールの出力を中間キャッシュとして保持し、変更があった段から下流だけを再計算する（例：リミッターだけを変えたときは、クリーンアップを再計算しない）。
- 処理が終わっていない区間は、UI 上で「処理中」とわかるように表示する（波形上の斜線パターンなど）。

### 8.2 再生モード

| モード | 内容 | ショートカット（案） |
|---|---|---|
| Before | 処理前 | `1` |
| After | 処理後 | `2` |
| Delta | 差分（処理後 − 処理前）を試聴 | `3` |
| Reference | リファレンス曲 | `4` |
| A/B トグル | 直前のモードと切り替え | `T` または `` ` ``（Tab はブラウザのフォーカス移動に使うため割り当てない） |
| **Loudness Match** | 比較時に、Before/Reference を After と同じラウドネスに揃えて再生する（**既定 ON**） | `M` |
| Platform Sim | 配信先の正規化を再現して再生（Spotify / Apple / YouTube） | メニュー |
| Mono | モノラルで確認 | `O` |

- すべてのモードはサンプル単位で同期しており、切り替えても再生位置は変わらない。
- ループ：範囲を選ぶ、またはセクション（自動推定）をクリックして設定する。`L` でループの ON/OFF。

### 8.3 スナップショット比較

- 設定の状態に名前を付けて保存する（例：「Cleanup 強め」「Loud 版」）。
- 2つのスナップショットを A/B で再生でき、波形も比較できる（8章の「Before」を任意のスナップショットに置き換える）。

## 9. 波形表示設計

### 9.1 表示する対象（ソース）

| ソース | 内容 |
|---|---|
| Before | 処理前（取り込んだ音源） |
| After | 処理後 |
| Diff | 差分。表現は 9.3 の3種類から選ぶ |

### 9.2 表示レイアウト（切り替え・同時表示）

| レイアウト | 説明 | 用途 |
|---|---|---|
| **Single（切り替え）** | 1つのソースだけを表示し、タブまたはキーで切り替える | 集中して見る |
| **Overlay（重ね）** | Before（グレーの塗り）と After（アクセントカラーの輪郭＋半透明の塗り）を重ねる。Diff をさらに重ねることも可能 | 音圧の変化・潰れ具合を直感的に見る |
| **Stacked（上下並び）** | Before / After / Diff を縦に並べ、時間軸・ズーム・カーソルを同期 | 3つを同時に詳しく比較する |

- レイアウトの切り替え：`V` で順番に切り替える。表示するソースはチェックボックスで ON/OFF（Stacked では最大3段）。
- **再生しているソースを強調表示**：現在聴いているモード（Before/After/Delta）の波形を太く・明るく表示し、「見ているもの」と「聴いているもの」が一致するようにする。

### 9.3 差分（Diff）の3つの表現

| 表現 | 内容 | わかること | 表示方法 |
|---|---|---|---|
| **差分信号**（Signal） | After − Before のサンプル差（ゲインを合わせるかどうかは切り替え可能） | 処理で変化した成分そのもの | 通常の波形と同じ形式（min/max） |
| **ゲイン変化**（Gain Δ） | 短時間 RMS（またはラウドネス）の比を dB で表した時系列 | どこでどれだけ音量が上がった/下がったか。リミッター・コンプの効き具合 | 0dB を中心線とした面グラフ。上方向＝ブースト（橙）、下方向＝カット（青） |
| **スペクトル差分**（Spectral Δ） | 時間 × 周波数ごとの dB 変化 | シマー・ヒスを**いつ・どの帯域で**除去したか | ヒートマップ（青＝カット、無彩色＝変化なし、橙＝ブースト）。対数周波数軸 |

### 9.4 波形の描き方（見やすさの工夫）

- **ピーク（min/max）と RMS を2層で描画**：外側の薄い塗り＝ピーク、内側の濃い塗り＝RMS。音圧（密度）がひと目でわかる。
- **縦軸の切り替え**：リニア / dB（dB 表示では小さい音の変化も見える）。
- **ラウドネス曲線のオーバーレイ**（任意）：Short-term LUFS を折れ線で重ね、目標 LUFS を水平の点線で示す。
- **マーカー**：True Peak の上限超え（赤い縦線ではなく▲記号＋色）、クリップ、セクションの境界、ループ範囲。
- **ゲインリダクションの帯**（任意）：リミッターがかかった量を波形の上端に細い帯で表示。
- **ミニマップ**：曲全体の縮小波形を上部に表示。表示範囲を枠で示し、ドラッグで移動。
- **ズーム**：ピンチ / `Cmd + スクロール` / `+` `-`。サンプル単位まで拡大できる（複数解像度のピークキャッシュで実現）。
- **色**：Before＝ニュートラルグレー、After＝アクセント（シアン系）、Diff＝青/橙の発散配色。ライト/ダークテーマの両方で確認し、色覚多様性に配慮して色以外の手がかり（線種、記号、ラベル）を併用する。

### 9.5 アルバム俯瞰ビュー

- 全曲を横一列（タイムライン）または縦のリストで表示する。
- 各曲の縮小波形（After）、Integrated LUFS のバー、トーン偏差のインジケーター、警告アイコンを表示する。
- 曲間（ギャップ）とフェードを、タイムライン上でドラッグして編集できる。

- 書き出し前のチェック：TP 超え、クリップ、極端な音圧、モノラル互換性の低下、サンプルレートの不一致。

## 11. データ設計（概要）

### 11.1 保存場所

ブラウザは、一度閉じたローカルファイルのパスを後から開き直せない。そのため、**取り込んだ音源はブラウザ内ストレージ（OPFS）にコピー**して保持する（元のファイルは変更しない）。

| 保存先 | 内容 |
|---|---|
| IndexedDB | プロジェクト一覧、各プロジェクトの設定・曲リスト・曲順・曲間・アルバム設定・スナップショット・解析結果、アプリ設定 |
| OPFS `/sources/` | 取り込んだ音源のコピー（デコード前の元ファイル） |
| OPFS `/cache/` | 中間レンダリング、波形ピーク、スペクトログラム（再生成できるもの。容量が足りなければ削除する） |

- 起動時に `navigator.storage.persist()` を要求し、ブラウザに勝手に削除されないようにする。
- ストレージの使用量を設定画面に表示し、プロジェクト単位・キャッシュ単位で削除できるようにする。

### 11.2 プロジェクトファイル（バックアップ・共有用）

ブラウザ内のデータはその PC・そのブラウザにしか残らないため、**プロジェクトを1つのファイルに書き出し・読み込み**できるようにする。チームでの受け渡しにも使う。

```
MyAlbum.akmaster（ZIP 形式）
├── project.json             ← メタ情報、曲リスト、曲順、曲間、アルバム設定
├── tracks/
│   └── <track-id>/
│       ├── settings.json    ← 処理設定（共通設定との差分）
│       ├── snapshots.json   ← スナップショット
│       └── analysis.json    ← 解析結果（処理前・処理後）
└── sources/                 ← 元の音源（任意。含めない場合は、読み込み時に音源の再指定を求める）
```

### 11.3 主なエンティティ

| エンティティ | 主な属性 |
|---|---|
| Project | id, name, type(single/album), tracks[], albumSettings, createdAt, version |
| Track | id, title, sourceRef, order, gapAfterSec, fadeIn/Out, settings, analysisBefore/After |
| ProcessingSettings | cleanup{…}, eq{…}, dynamics{…}, saturation{…}, stereo{…}, limiter{…}, macros{…} |
| AlbumSettings | anchorTrackId, toneMatchAmount, commonPreset, loudnessTarget, tpCeiling |
| Snapshot | id, name, settings, createdAt |
| AnalysisResult | loudness{…}, spectrum{…}, stereo{…}, artifacts{…}, sections[], peaksRef |

- settings にスキーマのバージョンを持たせ、将来の変更に備えてマイグレーションできるようにする。

## 12. 入出力仕様（概要）

| 区分 | 仕様 |

## 13. 品質保証の方針（概要）

- **DSP の単体テスト**：True Peak の上限を守れているか、ラウドネス目標の誤差（±0.5 LU 以内）、無処理（バイパス）時にビット単位で一致するか、位相・遅延の補償。
- **ゴールデンテスト**：代表的な Suno 楽曲 10〜20 曲で、出力の指標（LUFS、TP、シマースコアの減少率など）が回帰していないかを確認する。
- **試聴評価**：開発中にブラインドの A/B テスト（ラウドネスを揃えて）を行い、クリーンアップの既定値を調整する。
- **性能テスト**：NFR-01〜04 の計測。

## 15. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| シマー除去の副作用（こもり、トランジェントの劣化） | 音質への不満 | トランジェント保護、かけすぎの警告、デルタ試聴で確認できるようにする、P0 で試聴評価 |
| Suno のモデル更新でアーティファクトの傾向が変わる | 既定値がずれる | 検出指標と既定値の表を外部設定化し、ゴールデンテストを更新しやすくする |
| DSP をすべて自前で実装する工数 | 開発期間 | 処理の種類を最小限に絞る（MVP は 4.2 の段に限定）。P0 で Python 試作 → Rust 移植の流れを確立する |
| ブラウザのメモリ制限（特に Safari） | 長い曲・アルバムで落ちる | 1曲ずつ処理し、使っていないデータは OPFS に逃がす。Worker の数をメモリに応じて制限する |
| ブラウザ内ストレージの削除・容量不足 | 作業データが消える | `storage.persist()` の要求、使用量の表示、プロジェクトファイルへの書き出し（11.2）を案内する |
| Safari の機能不足・挙動の違い | 一部機能が使えない | 3.4 の代替手段。P0 で Safari を重点的に検証し、E2E テストに WebKit を含める |
| ML モデルのサイズ・速度・ライセンス | ダウンロード量、処理時間 | 任意機能とし、初回使用時にだけダウンロードして OPFS に保存する。重みのライセンスを個別に確認 |

## 16. 用語集

| 用語 | 説明 |
|---|---|
| LUFS | ラウドネスの単位（ITU-R BS.1770）。人の聴感に近い音量 |
| dBTP | True Peak。サンプル間のピークも含めた最大値 |
| LRA | ラウドネスレンジ。曲の中の音量の幅 |
| PLR | Peak to Loudness Ratio。ピークとラウドネスの差。小さいほど潰れている |
| シマー（Shimmer） | Suno 特有の、高域のガラスっぽい・揺らぐ質感のアーティファクト |
| デルタ試聴 | 処理前後の差分だけを聴くこと |
| アンカー曲 | アルバムのラウドネス基準にする曲 |
| M/S | Mid（中央）/ Side（左右の差）に分けて処理する方式 |
| ディザ | ビット深度を下げるときに量子化歪みを抑えるための微小なノイズ |
| SRC | サンプルレート変換 |
| ステム | パート別の音源（ボーカル、ドラム、ベース等） |
